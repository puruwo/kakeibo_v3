KAN-83 / 戦略A（1枚）

収入カテゴリーを編集できるようにする

ブランチ: claude/KAN-83 ← dev ／ DB スキーマ変更: なし ／ マイグレーション: なし
v2 — 大カテゴリーの新規追加・編集・削除（id=1, 2 を除く）に対応

1. ゴール

  • カテゴリー設定ページに 「収入」タブ を追加する。
  • 大カテゴリー:
    • 新規追加 ✅
    • 編集（名前/アイコン/色） ✅
    • 削除 ✅（id=1（月次収入）/ id=2（ボーナス）は不可）
    • 並び替え・表示ON/OFF ❌（スキーマ変更しないため）
  • 小カテゴリー: 追加・編集・削除・並び替え・表示ON/OFF（支出と同等）
  • 既存の expense / fixedCost の編集 UI には極力影響を与えない。
絶対条件: id=1（月次収入）／ id=2（ボーナス）の 2 レコードは アプリ全体でハードコード参照されているため 削除・ID 変更を許容しない。 Repository / Usecase / View の 3 層でガードする。

2. 仕様サマリ

観点支出（一般）固定費収入（本チケット）
大カテ 追加可可可 変更
大カテ 削除可可可（id≧3 のみ） 変更
大カテ 編集（名前/アイコン/色）可可可
大カテ 並び替え/表示切替可可不可
小カテ 編集可なし可
DB カラム追加——なし

3. 削除時の挙動

  • id≧3 の大カテゴリー削除時、紐づく小カテゴリーをすべて削除。
  • 削除する小カテゴリーで登録された income レコードも削除（支出側と同等の挙動）。
  • id=1 / id=2 では削除ボタン自体を非表示／無効化（View）＋ Usecase でも例外を投げる。

6. リスク

  • id=1/2 ガード漏れ: View の削除ボタン非表示だけだと不十分。Usecase / Repository でも if (bigId == 1 || bigId == 2) throw の二重ガードを入れる。
  • 削除時のカスケード: 大カテゴリー削除 → 小カテゴリー削除 → 紐づく income レコード削除を transaction で実施する（途中失敗時の整合性を担保）。
  • IncomeSmallCategoryEntity.update() 既存バグ（expense テーブルに書いている）を修正するが、 現状未使用なので他機能への影響なし。
  • allIncomeBigCategoriesProvider を updateDBCountNotifier 監視に変更しても、 既存の収入入力画面は再取得タイミングが少し増えるだけで実害なし。
ID=1（月次収入） / ID=2（ボーナス）は 3 層でガード:
① View（削除ボタン非表示） ② Usecase（deleteBig 入口で例外） ③ Repository（delete 入口で例外）
